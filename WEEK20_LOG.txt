TASK 1: simulate_training_pairs.py
====================================

Blueprint context: 4ypblueprint.pdf's recommended Track B DL quantification
architecture (Paper 2, Dumont Le Brazidec 2024 -- U-Net segmentation ->
CNN regression, MC-dropout uncertainty, physics-guided loss) was never
built in this project. Track B ended up pure physics (physics_ime.py /
physics_gaussian_crosssection.py) and Track A's CNN is detection-only.
Stage 1 of that architecture needs labeled (XCO2 tile, plume mask, true Q)
training pairs, and no real labeled dataset exists at this project's
scale -- the same reason SMARTCARB used a transport model instead of real
labels.

simulate_training_pairs.py generates these synthetically, reusing
plume_model.py (this project's own validated Briggs/Pasquill-Gifford
Gaussian plume physics) as the simulation engine -- no external transport
model imported. Pipeline: sample (Q, wind speed, wind direction, stability
class, stack height) per tile from ranges drawn from this project's own
real data (data/emission_estimates.json, data/plant_results.json) ->
evaluate the plume physics on a 60km/64px grid matching Track A's actual
export_facility_tiles.py convention (~937.5 m/px, NOT an arbitrary finer
grid) -> convert ground-level concentration (kg/m^3) to column XCO2
enhancement (ppm) via an explicit H_PBL_M=800m boundary-layer-height
assumption, then inverting physics_ime.py's own column_mass_enhancement()
-> add 415ppm background + 0.8ppm sounding noise (matches plant_results.json's
real bg_std_ppm scale) -> apply randomized rectangular cloud-gap masking
(15-55% NaN per tile, a simplification -- real cloud fields aren't
rectangles, flagged not hidden) -> save both positive (plume) and negative
(background-only) tiles.

Three known issues, already found and fixed in a prior debugging pass,
implemented directly here:

  BUG 1 (near-field singularity): plume_model.ground_level_concentration()'s
  own guard (x_safe = np.where(x_m > 1.0, x_m, 1.0)) only prevents a
  literal div-by-zero, not the unrealistic spike within the first few tens
  of meters of the source (sigma_y/sigma_z are still ~0 at x=1m). Fixed by
  NOT calling plume_model.plume_grid() -- this script recomputes the
  downwind/crosswind rotation locally (same formula as plume_model.py's
  own module docstring), clips downwind_x to max(3*H_m, 300) before
  evaluating concentration, and zeroes true-upwind pixels (downwind_x<=0).
  This same latent gap likely exists in build_plume_maps.py -- flagged as
  a possible follow-up, NOT modified here (paper-facing figures, out of
  scope).

  BUG 2 (wind-speed floor): sampling down to 0.5 m/s produced near-calm
  1/U-singularity outliers. The real per-overpass wind estimates in
  data/emission_estimates.json never go below 1.226 m/s across all 24
  facilities -- WIND_SPEED_RANGE floors at 1.2 m/s, justified by that real
  data.

  BUG 3 (resolution mismatch): tile pixel size fixed at SIZE_KM=60, PX=64
  (~937.5m/px) to match export_facility_tiles.py, not a finer arbitrary
  grid (which would under-sample the spatial averaging real satellite
  pixels naturally provide).

Verification: 55/55 tests pass (tests/test_simulate_training_pairs.py,
9 new tests, plus the existing 46). Script runs end-to-end, writes
data/simulated_train/simulated_tiles.npz (600 positive + 300 negative
tiles, masks, q_t_per_year) and simulated_tiles_meta.json (per-sample
params + calibration report).

TASK 2: per-pixel area-averaging -- verified improvement, tail NOT resolved
==============================================================================

Problem carried over from the prior debugging pass: point-sampling the
analytic concentration function at each pixel's center produces a
realistic median tile but an unrealistic high tail (point-sampling misses
the spatial averaging a real satellite footprint naturally provides).
Fix implemented: area_averaged_concentration_kg_m3() evaluates each
pixel on a 5x5 subgrid spanning its own ~937.5m footprint and averages,
rather than sampling once at the pixel center (Task 2's "real fix").

Step 1 -- confirm it's not a discretization artifact: reran the
worst-case parameter combo (max real Q=4.9e7 t/yr, min real wind=1.2 m/s,
stability A, stack=150m) at increasing subgrid density:

  N=1 (point sample):  60.4 ppm
  N=3:                 87.3 ppm
  N=5 (used):          92.0 ppm
  N=9:                 92.8 ppm
  N=15:                92.8 ppm
  N=25:                92.8 ppm

Converges cleanly by N=9 -- area-averaging is implemented correctly and is
NOT itself introducing noise or instability. (Note it converges to a
HIGHER value than the single-point sample here, not lower -- averaging
over the pixel picks up more of the near-peak region than the arbitrary
point-sample location did. Area-averaging is a correctness fix for how a
satellite footprint is sampled, not a mechanism that is guaranteed to
suppress peaks.)

Step 2 -- measure the actual effect on the full distribution, point
sampling (N=1) vs area-averaging (N=5), 600 positive tiles, same seed=42:

                  min    p10    median   mean    p90     p99     max
  point (N=1):   0.215  0.868   5.741   18.839  53.663  140.907  282.716
  area-avg (N=5): 0.245  0.659   4.654   13.292  39.129   80.888  130.739

Real reference range (data/plant_results.json co2_enhancement_ppm, N=24):
  -1.277 to 3.698 ppm.

Area-averaging DOES help substantially and consistently across the whole
distribution (max cut by more than half, p99 cut by ~43%, mean cut by
~29%) -- this is a real, verified improvement, not noise. But it does
NOT fix the tail to the standard set for this task: even the MEDIAN tile
(4.65 ppm) already exceeds the real observed maximum (3.70 ppm) across
all 24 facilities, and only 44.7% of positive tiles land within the real
range at all. Per this project's convention (WEEK13_LOG.txt's Rihand
investigation), this is reported as an honest partial/negative result
rather than force-fit with another parameter patch.

Root cause, diagnosed rather than guessed: this is NOT the independent-
parameter-sampling artifact it might look like (i.e. pairing an
unrealistically-high Q with an unrealistically-low wind speed that never
co-occurs in reality). Checked directly against data/emission_estimates.json:
Rihand -- a REAL facility already flagged in this project's own history
(Week 13) as a poorly-explained physics outlier -- has Q=4.835e7 t/yr
(the actual dataset maximum) and wind=1.294 m/s (near the actual dataset
minimum, 1.226), i.e. almost exactly the "worst case" combination used in
the Step-1 convergence check above. corr(Q, wind speed) across all 24
facilities is only -0.34 -- not a co-occurrence artifact.

So the real cause is more fundamental: physics_ime.py's Q is a mass-
balance estimate, derived by INTEGRATING XCO2 excess over a wide
near-plant zone (NEAR=0.25 of plume length) against a background annulus
much farther out -- it represents a total downwind flux, not a
point-source stack-top emission rate in the sense a forward Gaussian
plume equation expects at near-field range. Plugging that same Q back
into plume_model's near-field Gaussian formula (evaluated within ~300m-1km
of the stack, which is exactly what a 937.5m pixel near the plant
necessarily samples) reproduces the ORIGINAL problem this project already
found with the raw IME estimates: they are frequently overestimates
(Week 12: median bias 0.69x, r(log) 0.236 vs CEA; Rihand specifically at
+134%) -- and a forward near-field simulation using an already-inflated Q
naturally produces implausibly high near-source concentrations. This is
consistent with, not independent of, this project's existing Track B
accuracy findings; it is not a new bug in the simulator.

VERDICT: Task 2's area-averaging fix is implemented correctly and
verified to meaningfully improve tile realism, but does not close the gap
to a fully realistic peak-enhancement distribution -- the residual tail
traces back to physics_ime.py's own known Q-accuracy limitations
(documented since Week 12-13), not to a fixable simulator artifact.
Per the explicit instruction for this task, the U-Net (stage 1 of the
blueprint's Paper 2 architecture) is NOT started this session -- Task 2
is not "genuinely verified" as producing a realistic full distribution,
only genuinely verified as an improvement with a diagnosed, reported
limitation. Candidate next steps for a future session (not started):
(a) train the U-Net on this data anyway but explicitly note the label
distribution shift as a caveat, (b) cap simulated Q at a value informed
by CEA ground truth rather than raw IME estimates (would directly test
whether Q-accuracy, not simulation mechanics, is the real constraint),
(c) revisit whether a near-field exclusion larger than 3*stack-height is
physically justified given how IME's Q is actually defined.

TASK 3 (follow-up, same session): CEA-sourced Q retest -- tail gap
PERSISTS, and gets WORSE, ruling out Q source as the fixable variable
========================================================================

Before touching the simulator again, compared CEA's Q distribution SHAPE
to IME's, since if the shapes are similar, recalibrating which Q source
feeds the simulator can't close a shape-driven gap (any median-preserving
rescale is still the same shape). P95/median ratio, matched N=24
facilities (data/cea_ground_truth_2020_21.json vs
data/emission_estimates.json):

  CEA (matched N=24):  P95/median = 2.576   (P5/median 0.320, max/median 3.133)
  IME (matched N=24):  P95/median = 5.549   (P5/median 0.155, max/median 6.896)

IME's distribution is ~2.2x more right-skewed than CEA's -- a genuine
shape difference, not just scale. This made testing CEA-sourced Q a
legitimate next step, not a repeat of the same range under another name.

Changed Q_T_PER_YEAR_RANGE from the raw IME q_t_per_year range
(3.4e5, 4.9e7) to the CEA ground-truth abs_emissions_t_co2 range
(2.061e6, 3.321e7 -- RayalSeema min, Vindhyachal max, N=30 facilities)
and reran with area-averaging (N=5) unchanged. Full distribution, 600
positive tiles, same seed=42:

                    min    p10    median   mean    p90     p99     max
  IME-range (Task2): 0.245  0.659   4.654   13.292  39.129   80.888  130.739
  CEA-range (Task3): 1.375  2.908   9.838   14.821  33.968   62.866   98.633

Real reference range (data/plant_results.json co2_enhancement_ppm, N=24):
  -1.277 to 3.698 ppm.

Result: the tail gap did NOT close -- it got WORSE at the median and low
end. Median more than doubled (4.65 -> 9.84 ppm, now ~2.7x the real
observed max), and the fraction of positive tiles landing within the
real range DROPPED from 44.7% to 16.3%. Cause, verified analytically:
peak enhancement scales ~linearly with the log-uniform-sampled Q's
geometric mean (sqrt(min*max)). CEA's range floor (2.06e6 t/yr) is ~6x
higher than IME's floor (3.4e5 t/yr) -- even CEA's SMALLEST facility is
still a large point source -- so CEA's narrower, less-skewed range has a
HIGHER typical (geometric-mean) Q than IME's wider range did, and this
forward near-field simulator produces a correspondingly higher typical
ppm. The P90/p99/max did drop somewhat (consistent with CEA's smaller
top-end skew), but not enough to offset the worse median, and the
distribution as a whole is not closer to real observations by any
reasonable measure.

This directly answers the standing question: capping Q to real,
independently-sourced (non-IME) ground truth did not fix the tail --
it made the bulk of the distribution worse. That rules out "Q source"
(IME vs CEA, or any single-range recalibration) as the fixable variable,
and points at the deeper structural issue flagged as a possibility in
this task's own framing: physics_ime.py's IME (mass-balance: integrate
XCO2 excess over a wide near-plant zone vs. a background annulus, at
whatever real per-overpass wind existed) and this script's forward
Gaussian model (ground-level point-source dispersion at near-field
range, under an assumed boundary-layer height) are two different
physical formulations of "Q" that are not mathematical inverses of each
other. IME's Q is calibrated to reproduce a spatially-INTEGRATED mass
excess over a multi-km zone under real, varied wind conditions; this
script's forward model evaluates a point-source Gaussian plume at a
937.5m pixel close to the stack, under sampled (not matched-to-any-real-
day) wind conditions. There is no reason to expect ANY choice of "true"
Q -- IME's own estimate, CEA's ground truth, or anything in between --
to reproduce a realistic near-field ppm under this forward model, because
the mismatch is in the FORWARD FORMULATION, not the input.

VERDICT: this is reported as an open, paused negative result, following
the same diminishing-returns discipline as WEEK13_LOG.txt's Rihand
investigation. Two genuinely different Q sources were tested (IME's own
range, then CEA ground truth) and the second, more independently-
grounded choice made the realism gap WORSE, not better -- continuing to
patch the Q range further is not expected to help and is not attempted.
The forward-simulator/inverse-IME formulation mismatch is the leading
candidate explanation but has NOT been independently confirmed (e.g. by
building a genuine second forward model that integrates over a
near-plant zone the way IME does, and checking whether THAT reproduces
realistic ppm) -- that would be the next real test, not a Q-range patch.
The U-Net (blueprint Paper 2 stage 1) remains NOT STARTED. This is
explicitly left open/paused, not resolved, pending either that
independent confirmation or a different methodological approach to
generating training labels (e.g. training the U-Net on tiles labeled by
a mass-balance-style forward model consistent with how IME itself
defines Q, rather than a stack-top Gaussian dispersion model).

TASK 4: IME-consistent Q readout -- confirms the forward/inverse
formulation mismatch directly, does not close the gap (flips it instead)
========================================================================

Task 3 left open the possibility that comparing a single hottest-pixel
readout to a Q value estimated by a completely different method (IME's
spatial mass-balance) was never a fair realism check in the first place.
This task tests that directly, WITHOUT changing the underlying physics:
the 2D concentration field is still genuine Gaussian plume dispersion
with the BUG 1 near-field guard and Task 2 area-averaging unchanged. Only
the READOUT changed -- replaced the single peak pixel with
physics_ime.py's own near-plant/background-annulus geometry (NEAR=0.25
deg, BG_IN/BG_OUT=0.4/0.9 deg, ~27.75/44.4/99.9 km at the ~111 km/deg
conversion this project's own comments already use), computing
mean(near-zone) - mean(background-annulus) -- exactly
process_plant.py's co2_enhancement_ppm definition. Because that
background annulus (out to ~100 km) doesn't fit inside Track A's 60km
training tile, this readout is evaluated on a separate, larger
calibration-only grid (see SIMULATOR_METHODOLOGY_NOTE.md and the
module docstring) -- never saved as a training tile.

Full distribution, 600 positive tiles (Q still CEA-range per Task 3),
same seed=42, vs. the REAL full distribution (not just min/max --
computed here for the first time this session):

                        min     p10    median   mean    p90     p99    max
  simulated (IME readout): -0.040  0.003   0.054   0.072   0.163   0.327  0.562
  real (plant_results.json,
        co2_enhancement_ppm,
        N=24):              -1.277 -0.866   0.619   0.620   1.839   3.409  3.698

Negative (no-plume) tiles, sanity check (should be ~0): median 0.002,
p90 0.033, max 0.071 -- correctly small, confirms the readout mechanism
itself isn't biased.

Naive result: 100% of positive tiles fall within the real [-1.277, 3.698]
min/max envelope (up from 12.8% under the old peak-pixel readout on the
same run). Taken at face value that looks like a fix. It is NOT: the
real distribution's median is 0.619 ppm; the simulated median is 0.054
ppm -- more than 10x smaller -- and the simulated MAX (0.562) does not
even reach the real MEDIAN. The min/max containment check passed only
because the simulated distribution collapsed almost entirely toward
zero, not because it now resembles the real distribution's shape. This
is the same lesson as Task 3's "check the shape, not just the range"
principle turned back on this task's own result -- reported honestly
rather than claimed as a fix.

Cause, verified analytically, not guessed: computed the Gaussian plume's
sigma_y (1-sigma crosswind half-width) at the near-zone's outer radius
(27.75 km), stability class B: 2285 m. A near-zone DISK of that radius
has area ~2419 km^2 and circumference ~174 km; the plume's ~2-sigma
core width at that radius is ~4.6 km -- only ~2.6% of the disk's
circumference. For a SINGLE fixed wind direction (each synthetic tile
samples exactly one), more than 97% of the near-zone disk sits at pure
background, so averaging over the whole disk dilutes the plume signal
by roughly two orders of magnitude relative to the plume's own peak.
Real near-plant soundings, by contrast, are NOT one snapshot -- they are
whatever OCO-3 soundings landed within that disk across MANY overpass
days over up to a year, each day potentially carrying a DIFFERENT real
wind direction, so different days' plumes sweep different wedges of the
disk and the accumulated "near" sample captures elevated readings from
several directions, not just one. A single synthetic tile with one
sampled wind direction structurally cannot reproduce that -- it is
comparing a single-day snapshot's spatial mean to a multi-day aggregate
by construction, not a like-for-like readout.

VERDICT: this CONFIRMS, rather than merely leaves open, the possibility
flagged going into this task -- physics_ime.py's inverse mass-balance
method (Q fit to reproduce a many-day-aggregated near/background
difference, via an assumed effective velocity/length scaling, not
literal forward dispersion) and this script's forward Gaussian
point-source model (single-snapshot, single-wind-direction dispersion at
near-field range) are genuinely different formulations of "Q" that do
not invert each other under any evaluation scale tried: point-sampling
the peak pixel over-shoots the real range by 1-2 orders of magnitude
(Task 1/2), and IME-style disk-integration under-shoots it by about the
same amount in the other direction (Task 4), for the identical
underlying field and the identical Q. Both directions of failure trace
to the same root cause -- a forward model evaluated at ONE wind
direction cannot be read out, at ANY single spatial scale, to match a
quantity whose real-world definition is implicitly averaged over MANY
wind directions across a year of overpasses.

This is reported as an OPEN, PAUSED negative result, per the explicit
instruction and this project's own diminishing-returns discipline
(WEEK13_LOG.txt). No further Q-range or readout-geometry patching is
attempted past this point. See SIMULATOR_METHODOLOGY_NOTE.md for the
consolidated design history (near-field fix, wind floor, resolution
match, area-averaging, Q-source falsification, forward/inverse
consistency) and the two candidate paths forward that were NOT
attempted this session: (a) simulate multiple wind-direction draws per
plant and aggregate their near/bg means before computing the readout,
which would test the diagnosis above directly but is a materially larger
scope change than a readout-geometry fix, or (b) abandon single-snapshot
forward simulation as the training-label source entirely and generate
segmentation masks/Q labels through a method structurally consistent
with IME's own multi-day aggregation assumption. The U-Net (blueprint
Paper 2 stage 1) remains NOT STARTED.

TASK 5: multi-day aggregation, implemented as candidate (a) above --
SECOND confirmed negative result. Recommend pausing this
sub-investigation.
========================================================================

Implemented candidate (a) from Task 4's close-out, under a strict
scoping constraint: the fix applies ONLY to the calibration/verification
readout. Each individual training tile remains exactly the single-
snapshot mechanism of Tasks 1-4 (one wind direction, one day, its own
exact mask, saved unaggregated) -- make_tile() now optionally accepts a
pre-drawn (Q, wind_speed, stack_height, stability) so several tiles can
share one synthetic facility's physical characteristics, but ALWAYS
resamples wind_from_deg fresh per call, and every tile is still generated
and saved through the identical code path as before. This is a disclosed
structural change to how tiles are GROUPED downstream (by facility, not
independently), not to how any individual tile is generated -- see
SIMULATOR_METHODOLOGY_NOTE.md for the full scoping argument.

n_days per synthetic facility was NOT an arbitrary constant: bootstrap-
sampled directly from the real per-facility hit_days values in
data/plant_results.json (N=30: min 1, max 25, median 8, mean 9.93,
HIT_DAYS_POOL in simulate_training_pairs.py). 200 synthetic facilities
were simulated (chosen for runtime, not to hit a target number), giving
1936 total single-snapshot positive tiles (well over the 500-tile
standard from prior rounds) plus 300 negative tiles -- 2236 tiles total,
67.8s wall time.

For each facility, multi_day_ime_readout_ppm() pools ALL n_days' raw
near-zone and background-annulus pixel samples (concatenated, exactly
matching physics_ime.py's own pooling: raw soundings across days
concatenated, THEN a single mean taken -- not an average of per-day
scalars) into one pooled readout. Full distribution, 200 pooled facility
readouts, vs the single-day (Task 4) distribution and the real
distribution:

                              min     p10    median   mean    p90    p99    max
  single-day (Task 4, this run): -0.086  0.000   0.057   0.075   0.180  0.293  0.437
  pooled multi-day (Task 5):     -0.048  0.010   0.058   0.076   0.174  0.255  0.410
  real (N=24):                   -1.277 -0.866   0.619   0.620   1.839  3.409  3.698

Result: pooling did NOT close the gap. The pooled median (0.058 ppm) is
statistically indistinguishable from the single-day median (0.057 ppm)
-- both remain >10x smaller than the real median (0.619 ppm). 100% of
facilities land within the real [-1.277, 3.698] min/max range, same as
Task 4's single-day result and, per Task 4's own finding, still a
misleading pass for the same reason (distribution collapsed near zero,
not shaped like the real one).

What DID change, precisely: pooling narrowed the SPREAD slightly (max
0.437->0.410, p99 0.293->0.255, min -0.086->-0.048) but left the CENTER
essentially unmoved (median/mean flat to three decimal places). Checked
directly: correlation between a facility's n_days (1 to 25, the real
range) and its pooled readout value is -0.018 -- statistically zero.
More pooled days produces NO systematic increase in the readout,
regardless of how many days are pooled.

Cause, verified analytically: this implementation's per-day sample is
the FULL near-zone/background-annulus GRID (thousands of pixels,
exhaustively covering every crosswind position), not a sparse
satellite-track sample. Because the grid already spatially integrates
over the ENTIRE disk on any single day, the "on-plume fraction" of that
day's near-zone pixels is already a stable expected value the moment one
day is evaluated -- pooling more full-disk days is mathematically close
to averaging several i.i.d. draws of an already-converged population
mean: it reduces the pooled estimate's NOISE (explaining the narrower
spread above) but cannot shift its EXPECTED VALUE, because the expected
on-plume fraction per full disk doesn't depend on how many additional
identical-composition disks get pooled in. A real per-overpass "near"
sample is NOT an exhaustive disk -- it is wherever OCO-3's actual,
narrow ground track happened to cross that day, so a day whose track
crosses the plume can contribute a near-zone sample that is
disproportionately plume-heavy (few points, many on-plume), and pooling
across many such days lets favorable-track days pull the aggregate up in
a way an exhaustive per-day grid mean structurally cannot. This is a
genuinely different mechanism than "more days of coverage" -- it is
"sparse, track-shaped sampling occasionally aligning with the plume,"
which this implementation did not simulate.

VERDICT: SECOND confirmed negative result. Multi-day aggregation, as the
most direct and literal translation of the Task 4 diagnosis into an
implementation, does not close the gap, and the reason it doesn't is now
also understood analytically rather than left as a mystery: the fix
addressed "one wind direction" but not the other real-world ingredient
the diagnosis actually depended on -- sparse, orbital-track-shaped
per-day sampling, not exhaustive per-day spatial coverage. Simulating
that properly (real OCO-3 orbital geometry, sounding density, and swath
width per overpass) is a materially larger scope change than anything
attempted in this sub-investigation so far -- effectively building a
second, independent satellite-sampling simulator, not a readout-geometry
adjustment.

Five rounds have now been run against this gap: near-field/wind-
floor/resolution fixes (Tasks 1-2, both correct and kept), area-
averaging (Task 2, correct and kept, but insufficient alone), Q-source
falsification (Task 3, ruled out, made things worse), IME-consistent
readout geometry (Task 4, confirmed the forward/inverse mismatch but
flipped the error direction), and multi-day pooling (Task 5, confirmed
again, near-zero effect, now with a specific analytical cause). Per this
project's own diminishing-returns discipline (WEEK13_LOG.txt's Rihand
investigation, paused after four rejected explanations), this
sub-investigation is PAUSED here, not resolved. The remaining candidate
(simulating real orbital sampling geometry) is recorded in
SIMULATOR_METHODOLOGY_NOTE.md as the next real test, not attempted this
session. The U-Net (blueprint Paper 2 stage 1) remains NOT STARTED.

TASK 6: real OCO-3 SAM orbital sampling geometry -- a materially
DIFFERENT result from Tasks 3-5, not a clean third failure, but still
not full closure. PAUSED here, U-Net still not started.
========================================================================

Implemented OCO-3's Snapshot Area Mapping (SAM) instrument geometry
directly, replacing the exhaustive readout grid with sparse simulated
footprint sampling: individual footprints 1.6km (cross-track) x 2.2km
(along-track), approximated as a rectangle (not a true rhombus -- the
corner-area difference is small relative to the footprint-averaging step
itself, a simplification stated explicitly, not hidden). Frames of 8
footprints span a 12.8km swath; frames spaced contiguously along-track
at the 2.2km footprint dimension (a standard pushbroom-design assumption
used instead of an independently-sourced ISS ground-track speed, to
avoid citing an uncertain external constant). SAM mode covers an 80x80km
box via 7 parallel swaths x 37 along-track frames x 8 footprints = 2072
raw theoretical footprints per scan, before cloud/data-quality loss.
Background-annulus sampling (44.4-99.9km, doesn't fit inside an 80km
box, same geometric mismatch as Task 4) is modeled separately as a
sparser Poisson scatter, its density set as a calibrated fraction of the
near-zone's simulated density -- disclosed as the less rigorously
derived half of this fix, since deriving OCO-3's actual non-SAM routine
orbital sampling was out of this task's explicit scope.

Both the near-zone retention fraction (cloud/data-quality loss applied
to the 2072 raw footprints) and the background/near density ratio were
calibrated from 5 real facilities' actual sounding density -- not
invented: data/plant_results.json "soundings"/hit_days for near-zone raw
density (against this fix's own theoretical 783 near-zone-only footprint
count), data/emission_estimates.json "n_bg_before_month_filter"/hit_days
for background density:

  Sasan retention=0.496 bg_ratio=0.0372, Vindhyachal 0.534/0.0352,
  Talcher 0.132/0.0600, Rihand 0.485/0.0390, Tamnar 0.154/0.0359.
  RETENTION_FRAC_RANGE=(0.132, 0.534), BG_DENSITY_RATIO_RANGE=(0.0352, 0.0600).

Q is read back out using physics_ime.py's own, unmodified
estimate_emission_rate_from_arrays() applied directly to the sparse
simulated soundings -- NOT a hand-rolled near-mean-minus-bg-mean scalar
as in Tasks 4-5. This matters mathematically, not just as a sampling
change: IME_kg is a SUM of positive excess (soundings below background
contribute exactly zero, not a diluting pull toward zero the way an
unconditional mean does), and L_eff = sqrt(n_used * FOOTPRINT_AREA_M2)

TASK 8: direct mechanistic correction of the noise-floor bias -- FAILED
in two mechanistically distinct ways. Sub-investigation CONCLUDED, not
paused again. Final verdict.

Before writing any code: checked physics_ime.py's own comments and this
project's citations for a documented basis for option (b) (per-sounding
noise scaling with local signal strength). Found none -- physics_ime.py
discusses SAMPLING noise (bootstrap over near/bg populations) and
background-definition SENSITIVITY (diagnose_talcher.py's finding that
this is "a much larger error source than wind or IME-sampling noise for
plants with a thin/weak plume signal" -- itself a prior, independent
piece of evidence that this project has already flagged weak-signal
facilities as a known-harder case), but nothing suggesting real OCO-3
retrieval noise scales with local variability rather than being a flat
per-sounding value. Proceeded with option (a): a closed-form statistical
correction applied to physics_ime.py's OUTPUT, not a retuned
SOUNDING_NOISE_STD_PPM constant.

THE MECHANISM: clip(near_i - bg_mean, 0, None) is a rectified/censored
Gaussian. For an off-plume sounding (true enhancement 0) under noise
N ~ Normal(0, sigma), E[max(N,0)] = sigma/sqrt(2*pi) -- NOT zero -- and
Prob(N>0) = 0.5 -- also not zero. Verified bg_std (a real-world-
observable quantity, computable from any physics_ime.py run, real or
simulated) is a good estimator of sigma: this simulator's own bg-zone
std comes out ~0.776-0.81ppm against a true injected noise std of
0.8ppm.

ATTEMPT 1 -- correct IME_kg only (subtract n_near_total * bg_std /
sqrt(2*pi), converted to kg via column_mass_enhancement, from IME_kg
before computing Q): FAILED, systematically and badly. Tested against
all 5 real-facility validation replays with their own exact Task 7
retention:

  facility      uncorrected Q ratio   IME-kg-only corrected
  Sasan         0.970                 0.501
  Vindhyachal   0.955                 0.485
  Talcher       2.155                 0.183
  Rihand        0.788                 0.440
  Tamnar        2.003                 0.203

This made EVERY facility worse, including the two that were already
close to 1.0 uncorrected. Diagnosed why, not just observed: for Sasan,
n_soundings_used=3852 out of n_near_total=7343 -- almost EXACTLY the
~50% pure-noise baseline (3671.5 expected from Prob(N>0)=0.5 alone).
This means L_eff (=sqrt(n_used*area)) was ALSO overwhelmingly noise-
driven, not just IME_kg. The "good" uncorrected ratio for Sasan was an
ACCIDENTAL CANCELLATION between a noise-inflated numerator and a
noise-inflated denominator, not a genuine recovery -- correcting only
the numerator broke that cancellation instead of fixing the underlying
estimate. This is a materially deeper finding than Tasks 6/7's own
diagnosis reached: the near-zone dataset, as simulated, is dominated by
noise-driven false-positive detections even for LARGE, easy-to-detect
facilities, not only weak ones.

ATTEMPT 2 -- correct BOTH IME_kg and n_used/L_eff consistently
(subtract 0.5*n_near_total, the same Prob(N>0)=0.5 baseline, from
n_soundings_used before computing L_eff): mechanistically the correct
next step (fixing the numerator alone was internally inconsistent), but
FAILED differently -- through severe numerical instability, not a
systematic direction error. Full 200-facility result:

                    before (Task 7)   after (Task 8, both terms corrected)
  median bias       1.540x            1.037x   <- looks like a near-perfect fix
  mean bias         2.396             1.827
  sd(log ratio)     0.918             5.096    <- exploded, 5.5x worse
  within 2x         53.0%             48.5%    <- did NOT improve
  corr(log_ratio,
    true_Q)         -0.643            +0.255   <- weakened in magnitude but changed sign

The median moving to 1.037 looks, in isolation, like a near-perfect fix
-- exactly the kind of single-number result this task's own instructions
warned against trusting without the full picture. The full picture: 30
of 200 facilities produced absurd ratios (near-zero or as high as 44x).
Root cause: n_used_corrected = n_used - 0.5*n_near_total subtracts two
LARGE, comparable-magnitude quantities to get a SMALL residual (for
Sasan: 3852 - 3671.5 = 180.5) -- classic "difference of nearly-equal
large numbers" numerical instability. Small relative errors in the
~50%-baseline assumption (itself only exact in the infinite-sample
limit; real finite samples fluctuate around it) get massively amplified
in the small residual, which then sits in L_eff's denominator, further
amplifying the effect on Q. This is not a bug to patch further within
this approach -- it is the SAME statistical phenomenon (signal buried in
noise at the individual-sounding level) reappearing as an estimation-
variance problem once an attempt is made to explicitly separate them.
